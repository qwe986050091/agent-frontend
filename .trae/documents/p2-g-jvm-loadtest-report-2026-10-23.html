P2-G JVM 调优与压测实证报告

日期：2026-10-23 · 对象：agent 服务（simple-agent 1.0.0，Spring Boot 3.5 / LangChain4j 1.17.2）

配套工具：d:\code\agent\perf · 原始数据：perf/results/p2g-final/summary.json · 关联路线图：个人能力差距分析与 90 天补齐路线图

一句话结论：生产 -Xms128m -Xmx768m -XX:+UseG1GC 保持不变。 100 并发下三种 GC 配置全部 300/300 成功、p95 706–735ms；500 并发时约 47%–51% 的请求被 SSE 线程池快速拒绝（503），真正的瓶颈是「24 活跃 + 100 排队」的线程池容量，不是 GC。 ZGC 停顿接近零（≤0.06ms），但堆占用是 G1 的 1.8–2.8 倍、CPU 更高，4c4g / 768m 机器不建议切换； G1 调优参数（Xms=Xmx、MaxGCPauseMillis=100）没有带来吞吐收益，反而最大停顿与堆占用更差。

GC 结论： ① 三种配置在 768MB 堆下都没有 Full GC、没有 OOM，G1 最大停顿 16–19ms，远低于 SSE 的 p95（735–1360ms）， GC 停顿不是当前延迟的主因；② ZGC 停顿确实接近零，但堆占用是 G1 的 1.8–2.8 倍 （ZGC 需要并发标记/转移的空间与 CPU），试跑阶段曾观测到 676MB 峰值 —— 在 768m 堆上没有安全余量； ③ G1 调优（Xms=Xmx + MaxGCPauseMillis=100）把 GC 次数从 10 次降到 1–2 次，但最大停顿反而升到 26–34ms、 堆占用升到 338–446MB，吞吐没有提升，属于「用内存换更少的 GC 次数」，不适合 4c4g 生产。

四、瓶颈定位

4.1 第一瓶颈：SSE 线程池容量（24 活跃 + 100 排队）

500 并发时，agent_sse_active 峰值为 123–125（G1/ZGC/G1 调优）， 与代码里的「max 24 + queue 100 = 124 个在途」几乎完全吻合；超过的请求被 AbortPolicy 立即拒绝，表现为 503（246–265/500），而不是排队超时。 这正是设计上的快速失败，但也意味着单实例硬上限约 124 个在途对话。

100 并发时 300 个请求全部成功（24 活跃 + 76 排队），p95 735ms； 500 并发时请求要在队列里多等约 0.4–0.6s（TTFT p95 从 142ms 升到 472ms）， p95 升到 1.1–1.4s —— 延迟增长主要来自排队，而非 GC 或 CPU。

4.2 第二瓶颈：Tomcat 线程随连接数增长，但没有泄漏

线程峰值：100 并发 183–208；500 并发 331–396（G1 369、ZGC 347、调优 372）。 线程数随客户端连接增长，压测结束随进程回收；没有出现线程数持续攀升或 Full GC 的泄漏信号。 生产若把并发提高到数百，需同时关注 Tomcat 线程、堆外内存与文件描述符。

4.3 内存：G1 余量充足，ZGC 需更大堆

G1 在 100/500 并发下堆峰值仅 119/200MB（768m 的 15%/26%），余量充足； ZGC 为 332/356MB（43%/46%），且试跑峰值近 676MB；G1 调优为 381/338MB。 生产 4c4g 机器上还有 MySQL / PG / Redis / RocketMQ / Prometheus 等进程， JVM 堆不能只看 768m 本身上限，ZGC 的额外占用会挤压系统页缓存与其它进程。

五、参数结论与上线建议

保持现状（推荐）： 
ExecStart=/usr/bin/java -Xms128m -Xmx768m -XX:MaxMetaspaceSize=192m -jar /opt/agent/agent.jar
G1 默认参数在本负载下延迟、吞吐、内存三项均衡；100 并发 p95 735ms，无 Full GC； 500 并发时以 503 快速失败保护上游，符合现有「有界队列 + AbortPolicy」的稳定性设计。
  • 不要切换 ZGC（当前 4c4g / 768m）：停顿收益（16ms → 0.06ms）对 p95 的贡献被排队与上游延迟掩盖， 却带来 1.8–2.8 倍堆占用和更高 CPU；只有把堆提升到 1.5–2GB 且有 CPU 余量时再评估。
  • 不要设置 -Xms768m：G1 调优实验显示 GC 次数减少但最大停顿、堆占用变差，吞吐无提升； 固定大堆还会让 4c4g 机器的内存长期被 JVM 占住。
  • 容量规划以 124 在途为基线：若业务需要 >100 并发对话，优先在网关层排队/限流（429 + 重试提示）， 而不是无脑放大线程池；确实要扩容时，建议 max 48 + queue 200，并同步验证上游 LLM 限流、堆余量与 Tomcat 线程。
  • 监控告警：把 agent_sse_active > 100（容量 80%）与 503 比例 >5% 加入 Prometheus 告警； GC 侧关注 Full GC 次数与老年代峰值，而不是单次 Young GC 的毫秒数。
  • 生产 GC 日志：建议加 -Xlog:gc*:file=/opt/agent/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20M （本次压测已用同一格式），便于复盘；对吞吐影响可忽略。

七、压测过程中顺带修复

rag.enabled=false 启动失败：禁用 RAG 时 RagConfig 不再提供 EmbeddingStore/Path Bean，但 RagService、RagController 仍被组件扫描装配，启动时报 Parameter 1 of constructor in RagService required a bean of type 'java.nio.file.Path'。 已为两者补上 @ConditionalOnProperty(prefix="rag", name="enabled", havingValue="true", matchIfMissing=true)， 与配置注释「rag.enabled=false 时整套 RAG Bean 不装配」的语义一致；本次压测即以 RAG_ENABLED=false 启动验证通过，全量单测/verify 仍全绿。
